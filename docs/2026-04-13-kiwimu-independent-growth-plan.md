# Kiwimu 下一階段計劃

日期：2026-04-13

## 一句話決策

`kiwimu.com` 下一階段先維持為**獨立獲客產品**，不優先追求五站完全統一登入。

它目前最有價值的角色不是「會員中心入口」，而是：

- 低摩擦人格測驗入口
- 高意圖資料採集器
- 跨產品導流分流站
- 未來 V2 / 付費內容 / 月活動的前置轉換引擎

---

## 目前營運現實

這份計劃要建立在目前真的能跑的路徑上，而不是理想狀態。

- `shop.kiwimu.com` 目前仍屬於**可驗證交付候選**，付款、會員工作台、外部整合還沒完成真人驗證。
- 現在真正承接甜點訂購意圖的前台入口是 `https://map.kiwimu.com/menu`。
- 因此在 `shop` 完成穩定化之前，`kiwimu` 的主購買 CTA 應先導向 `map/menu`，不是直接把 `shop` 當作主 landing。
- `shop` 這一階段更適合被視為商品資料與下單能力來源，等驗證完成後再考慮升級成獨立前台商城。

---

## 為什麼先不要硬併 SSO

### 現況已經成立的事

- V1 / V1.5 免費測驗已能穩定承接流量與完成測驗。
- 完成測驗後已經有 GA4、行為資料、受眾建立、結果封存、跨產品導流。
- 測驗完成後可同步人格結果到 Moon Island 品牌資料庫，代表「資料價值」已開始變現前置化。

### 現在不該優先做的事

- 不該為了五站一致性，提早提高 `kiwimu` 首次使用門檻。
- 不該把首頁或主流程改成「先登入再體驗」。
- 不該把 `kiwimu` 降成其他站的附屬模組。

### 真正風險

如果現在先把 `kiwimu` 強行收斂進統一身份系統，最可能損失的是：

- 測驗完成率
- 新用戶願意留下資料的比例
- 廣告/自然流量的第一觸點效率

---

## 產品角色定義

未來 1-2 個階段內，`kiwimu` 的正式角色定義如下：

### 角色 1：獲客前台

- 用免費測驗承接自然流量、社群流量、廣告流量、QR 流量。
- 盡量降低首次體驗摩擦，讓用戶先完成測驗、先被理解。

### 角色 2：人格資料引擎

- 記錄完成測驗、結果類型、變體、來源、裝置、分享與回訪。
- 將匿名行為逐步轉成可識別、可分群、可再行銷的資料。

### 角色 3：跨產品分流器

- 把不同人格與不同意圖，送往最適合的下一站：
  - `map.kiwimu.com/menu`：目前正式運行中的甜點目錄與訂購入口
  - `shop.kiwimu.com`：未來穩定化後的商城前台 / 商品能力來源
  - `passport.kiwimu.com`：身份/護照/回訪任務意圖
  - `map.kiwimu.com`：品牌探索意圖
  - `V2 / 付費報告`：深度內容付費意圖

### 角色 4：未來變現前置站

- 將來真正變現的不一定是測驗本身，而是：
  - V2 深度報告
  - 月活動
  - 高級會員
  - 虛擬商品
  - 抽獎/限定權益

`kiwimu` 要先做的是篩出哪一群人最可能付錢，而不是先把所有人變成同一套會員。

---

## 這階段的北極星指標

核心問題不是「登入有沒有統一」，而是：

> `kiwimu` 是否能穩定把匿名測驗流量，變成可回訪、可分群、可轉單的高品質名單。

建議北極星：

`測驗完成後 30 天內產生任一下游轉換的用戶數`

下游轉換包含：

- 登入封存檔案
- 點擊跨站 CTA
- 進入 `map/menu` 並產生訂購意圖
- 完成 `map` 訂單提交或後續 `shop` 訂單
- 解鎖 V2 / 付費內容
- 回訪 archive 或結果頁

### L4：下游變現/留存

- menu_visit

- v2_unlock_success

- 30-day return

## 這階段要盯的 6 個 KPI

### 1. 測驗完成率

- `quiz_complete / quiz_start`
- 用來判斷前段體驗是否健康

### 2. 結果頁登入封存率

- `login_success / result_view`
- 用來判斷「人格檔案保存」這條路是否成立

### 3. 結果頁導流點擊率

- `cross_product_click / result_view`
- 拆成 `order_menu / passport / map / v2`

### 4. 導流後下游轉換率

- 例如 `map_order_submitted / click_order_menu_cta`
- 用來判斷哪一條路最值得加碼

### 5. 30 天回訪率

- `return_users_30d / completed_users`
- 判斷 `kiwimu` 是一次性工具，還是可經營產品

### 6. 可識別名單率

- `identified_users / completed_users`
- identified 定義：登入、留 email、能綁定到 profile、能進再行銷名單

## Phase 規劃

## Phase 1：把漏斗看清楚

時間：1-2 週

目標：

- 不改大產品方向
- 先把資料看清楚
- 找出最能產生下游轉換的人群與 CTA

交付：

- 明確的 funnel 定義文件
- 每週固定查看的 KPI 看板
- 事件命名與資料欄位對齊
- 下游轉換 mapping 表
- `map/menu` 與實際下單資料的歸因對齊方式

重點任務：

- 對齊 `quiz_complete / result_view / login_success / archive_view / outbound_click / downstream_conversion`
- 確保每個跨站點擊都帶：
  - source
  - mbti_type
  - variant
  - session_id
  - campaign
- 能把 `kiwimu -> map/menu -> order` 與 `kiwimu -> passport/map/V2` 的結果串回來
- 若 `map` 訂單最終寫進 `shop_orders`，需保留 `source` 與原始入口欄位，避免把前台入口誤判成 `shop`

成功標準：

- 能回答「哪一種人、從哪來、做完什麼後，最容易往下走」

---

## Phase 2：把結果頁變成分流機器

時間：2-4 週

目標：

- 提升測驗完成後的下一步行動率
- 不增加首次使用門檻

重點任務：

- 結果頁 CTA 收斂成 3 個主路徑：
  - 封存人格檔案
  - 前往甜點目錄 / 訂購
  - 解鎖更深報告
- CTA 文案按人格象限或結果群組做差異化
- 把 `map` 放在品牌探索次要路徑，不搶主轉換
- 在 `shop` 穩定前，不把 `shop` 當結果頁主 CTA 目的地
- archive/login 提示文案以「保存、比較、長期追蹤」為主，不用會員中心語言

成功標準：

- 結果頁主 CTA 點擊率提升
- 登入封存率或下游轉換率其中至少一項顯著上升

---

## Phase 3：開始做第一個真正變現點

時間：4-8 週

目標：

- 從資料產品進入收入產品

優先順序建議：

1. V2 深度報告
2. 月活動 / 高級會員
3. 虛擬商品或限定解鎖

理由：

- 這些最接近 `kiwimu` 用戶的原始需求：想更理解自己。
- 與 `shop` 的購買需求不同，變現路徑更自然。

成功標準：

- 有第一條「測驗完成 → 付費」的穩定閉環

---

## SSO 何時再回來處理

不是不做，而是設立明確 Decision Gate。

只有在以下任一情況成立時，才把「全面五站一體 SSO」拉高優先級：

- `kiwimu -> passport` 或 `kiwimu -> map/menu -> 後續商城流程` 的跨站回訪非常高，但重複登入明顯阻礙轉換
- 同一位用戶在多站活動頻繁，身份碎片化已影響經營
- V2 / 高級會員 / 點數權益需要跨站即時共享
- 客服或營運已經因為帳號不一致而造成實際成本

換句話說：

> **先用商業訊號證明「統一身份會賺更多」，再投入整併。**

---

## 接下來 7 天該做什麼

### 優先 1：拉出真實漏斗報表

- 先做最近 14-30 天的：
  - 來源分布
  - 完成率
  - 登入封存率
  - CTA 點擊率
  - 下游轉換率

### 優先 2：定義三條主 CTA

- `保存人格檔案`
- `前往甜點目錄 / 訂購`
- `解鎖更深內容`

### 優先 3：把下游 conversion 回寫對齊

- 確定 `map/menu`、`passport`、V2 都能被歸因回 `kiwimu`
- 若訂單最終落在 `shop` 表，也要看得出最初入口其實來自 `map/menu`

### 優先 4：先不碰大登入收斂

- 除非是修 bug，不主動改成強制統一登入入口

---

## 一句話原則

`kiwimu` 先當最強的獲客與分流站，再決定要不要成為五站統一身份的一部分。

先放大有效資料，再整合身份系統。
